# Embedding 数据隐私安全方案

## 一、风险分析

通过云服务模型进行 Embedding 时，文档分块内容以明文 JSON 发送到第三方 API，存在以下数据隐私风险：

| 风险等级 | 风险项 | 说明 |
|---------|--------|------|
| **高** | 明文传输 | 文档分块内容以明文 JSON 发送到第三方 API，包含企业/高校内部知识资产 |
| **高** | 服务商数据留存 | 多数云 API 服务条款允许将请求数据用于模型训练改进，数据可能被长期留存 |
| **中** | 向量可逆推断 | 研究表明 embedding 向量可通过对抗攻击还原出原始文本的大致语义内容 |
| **中** | 供应链风险 | API Key 泄露或服务商被入侵可能导致历史请求数据泄露 |
| **低** | 合规风险 | 涉密或含个人隐私的数据出境可能违反《数据安全法》《个人信息保护法》 |

### 1.1 数据泄露链路

```
文档上传 → 文档解析 → 文档分块 → Embedding 向量化 → 向量存储
                                  │
                                  ▼
                          原始文本明文 ──→ 云端 API（第三方）
                          {"input": ["分块文本1", "分块文本2", ...]}
                                  │
                                  ▼
                          服务商可能：记录日志、用于训练、缓存留存
```

### 1.2 典型攻击场景

| 攻击方式 | 攻击路径 | 影响 |
|---------|---------|------|
| API 中间人攻击 | 公网传输被截获 | 分块明文泄露 |
| 服务商内部泄露 | 云服务商员工/系统漏洞 | 批量知识资产泄露 |
| 向量反演攻击 | 从 embedding 向量推断原文 | 敏感语义信息泄露 |
| API Key 泄露 | 配置文件/代码/日志泄露 | 未授权调用，数据外泄 |

## 二、企业级解决方案

### 2.1 方案一：本地化 Embedding（推荐）

**核心原则：所有 Embedding 计算不出内网，数据从生成到存储全链路不经过第三方。**

```
┌─────────────────────────────────────────────────────────┐
│                        企业内网                           │
│                                                          │
│  ┌──────────┐    ┌──────────────┐    ┌──────────────┐   │
│  │ 文档分块  │───→│ Ollama 本地   │───→│  pgvector    │   │
│  │ (明文)   │    │ Embedding    │    │  向量存储     │   │
│  └──────────┘    │ (GPU推理)    │    └──────────────┘   │
│       ↑          └──────────────┘           │           │
│       │                                     │           │
│  ┌──────────┐                        ┌──────▼───────┐   │
│  │ MinIO    │                        │  RAG 语义检索 │   │
│  │ 文件存储  │                        │  余弦相似度   │   │
│  └──────────┘                        └──────────────┘   │
│                                                          │
│              数据全链路不出内网                             │
└─────────────────────────────────────────────────────────┘
```

**优势：**
- 数据隐私保护等级最高，零数据外泄风险
- 无网络延迟，Embedding 速度取决于本地 GPU 算力
- 无 API 调用成本，长期运营成本低
- 不受云服务商服务中断影响

**劣势：**
- 需要 GPU 服务器硬件投入
- 需要运维本地模型服务

**本地 Embedding 推荐模型：**

| 模型 | 参数量 | GPU 显存需求 | 向量维度 | 效果评估 | 适用场景 |
|------|--------|------------|---------|---------|---------|
| `qwen3-embedding:8b-fp16` | 8B | ~16GB | 1536（通过 `dimensions` 参数） | 优秀 | 有高端 GPU，追求最佳效果 |
| `bge-m3` | 0.6B | ~1.5GB | 1024 | 良好 | 资源有限，性价比首选 |
| `nomic-embed-text` | 0.1B | ~0.5GB | 768 | 中等 | 资源极度受限 |
| `mxbai-embed-large` | 0.3B | ~0.7GB | 1024 | 良好 | 通用场景 |

**系统配置：**

```yaml
ai:
  embedding:
    default-model: qwen-emb-local
    candidates:
      - id: qwen-emb-local
        provider: ollama
        model: qwen3-embedding:8b-fp16
        dimension: 1536
        priority: 1
        enabled: true
      # 云端模型仅作灾备，平时禁用
      - id: qwen-emb-4b
        provider: siliconflow
        model: Qwen/Qwen3-Embedding-4B
        dimension: 1536
        priority: 99
        enabled: false
```

**ai-shopping-agent 系统已有能力：** 当前 `RoutingEmbeddingService` 已支持按优先级路由和自动降级，`OllamaEmbeddingClient` 已实现本地调用，无需 API Key。只需确保生产环境 Ollama 可用且云端候选项 `enabled: false`。

### 2.2 方案二：数据脱敏 + 云端 Embedding（混合方案）

**适用场景：** 无 GPU 资源，需要使用更强云端模型，但文档含敏感信息。

**核心思路：** 在文本发送到云端之前，对敏感实体进行脱敏处理，保留语义结构的同时去除敏感信息。

```
原始分块文本 → 脱敏处理器 → 脱敏后文本 → 云端 Embedding → 向量
                  │
                  ├── 人名替换：张三 → [PERSON_1]
                  ├── 手机号替换：138xxxx → [PHONE_1]
                  ├── 身份证替换：510xxx → [IDCARD_1]
                  ├── 组织名替换：XX公司 → [ORG_1]
                  ├── 地址替换：XX路XX号 → [ADDR_1]
                  └── 专有名词哈希：核心技术名 → SHA256前8位
```

**脱敏策略：**

| 策略 | 方法 | 语义保留度 | 实现复杂度 |
|------|------|----------|----------|
| 实体识别+替换 | NER 识别敏感实体，替换为类别标签 | 高 | 中 |
| 关键词哈希 | 对专有名词做 SHA-256 哈希截断 | 中 | 低 |
| 差分隐私 | 在 embedding 向量上添加噪声 | 中 | 高 |
| 同态加密 | 加密状态下计算相似度 | 最高 | 极高 |

**实现位置：** 在 `ChunkEmbeddingService` 调用 `EmbeddingService.embed()` 之前增加脱敏处理器。

**架构示意：**

```
ChunkEmbeddingService
    │
    ├── 1. 获取原始分块文本
    ├── 2. 调用 SensitiveDataMasker.mask(text)  ← 新增脱敏层
    ├── 3. 将脱敏后文本发送给 EmbeddingService
    └── 4. 返回向量（与原始分块关联存储）
```

### 2.3 方案三：向量加密存储（纵深防御）

**核心思路：** 即使 Embedding 在本地生成，向量数据本身也需要加密保护，防止数据库泄露时向量被窃取。

**PostgreSQL 列级加密方案：**

```sql
-- 启用 pgcrypto 扩展
CREATE EXTENSION IF NOT EXISTS pgcrypto;

-- 加密存储向量（应用层加密，数据库层存储为 bytea）
-- embedding_encrypted = pgp_sym_encrypt(embedding::text, '密钥')
-- 查询时解密：pgp_sym_decrypt(embedding_encrypted, '密钥')::vector
```

**分层加密架构：**

```
┌─────────────────────────────────────────────────┐
│                  应用层                           │
│  Embedding 生成 → 向量加密 → 写入数据库           │
│  查询数据库 → 向量解密 → 相似度计算               │
└──────────────────────┬──────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────┐
│               PostgreSQL + pgvector               │
│  t_knowledge_vector.embedding_encrypted (bytea)  │
│  密钥由 KMS（密钥管理系统）管理                     │
└─────────────────────────────────────────────────┘
```

**密钥管理建议：**
- 使用独立的密钥管理系统（KMS），如 HashiCorp Vault、阿里云 KMS
- 密钥与数据分离存储，不放在同一数据库
- 支持密钥轮换，定期更换加密密钥

### 2.4 方案四：访问审计与数据生命周期管控

**此方案为所有场景的必做项，与其他方案组合使用。**

#### 2.4.1 Embedding 调用审计

| 审计项 | 记录内容 | 不记录内容 |
|--------|---------|-----------|
| 调用时间 | 时间戳 | - |
| 调用模型 | 模型 ID、provider | - |
| 数据量 | 文本条数、总字符数 | 原始文本内容 |
| 调用来源 | 知识库 ID、文档 ID | - |
| 返回状态 | 成功/失败、耗时 | 返回的向量值 |
| 网络来源 | 调用方 IP 地址 | - |

**实现位置：** `RoutingEmbeddingService` 中增加审计日志切面。

#### 2.4.2 向量访问控制

```
用户请求检索 → 鉴权 → 知识库级别权限校验 → 仅检索有权访问的向量空间
                                    │
                                    └── collectionName 与知识库绑定
                                        按 RBAC 权限控制检索范围
```

**ai-shopping-agent 系统已有基础：** `t_knowledge_base.collection_name` 与 `t_knowledge_vector.collection_name` 关联，RBAC 权限控制已实现。需要确保检索接口也走 `knowledge:read` 权限校验。

#### 2.4.3 数据留存策略

| 数据类型 | 留存策略 | 清理方式 |
|---------|---------|---------|
| 已删除文档的向量 | 立即清理 | 删除文档时同步删除向量（已实现） |
| 已禁用文档的向量 | 保留但不参与检索 | 检索时过滤 enabled=false 的分块 |
| 过期知识库 | 按业务需求定期清理 | 定时任务扫描 + 人工确认 |
| 审计日志 | 保留 180 天 | 定时任务清理过期记录 |
| Embedding 调用日志 | 保留 90 天 | 定时任务清理 |

## 三、方案对比与选型建议

| 方案 | 隐私保护等级 | 实施难度 | 硬件要求 | 适用场景 |
|------|------------|---------|---------|---------|
| **方案一：纯本地 Embedding** | ★★★★★ | 低（系统已支持） | 需要 GPU 服务器 | 数据高度敏感，有 GPU 资源 |
| **方案二：脱敏+云端** | ★★★☆☆ | 中 | 无额外硬件 | 无 GPU，需用强模型 |
| **方案三：向量加密存储** | ★★★★☆ | 中 | 无额外硬件 | 纵深防御，合规要求高 |
| **方案四：审计+管控** | ★★☆☆☆（辅助） | 低 | 无额外硬件 | 所有场景都应实施 |

### 3.1 推荐组合

**高校/企业知识库场景（推荐）：**
- **方案一 + 方案四** = 本地 Embedding + 审计管控
- 数据全链路不出内网，配合完善的审计日志和访问控制
- 适合：有 GPU 资源、数据敏感度高的场景

**资源受限场景：**
- **方案二 + 方案三 + 方案四** = 脱敏 + 加密 + 审计
- 数据脱敏后发送云端，向量加密存储，全链路审计
- 适合：无 GPU 资源、可接受一定隐私风险的场景

**最高安全等级场景：**
- **方案一 + 方案三 + 方案四** = 本地 + 加密 + 审计
- 全链路数据不出内网 + 向量加密 + 完整审计
- 适合：涉密数据、金融/政务等强合规场景

## 四、ai-shopping-agent 系统改造要点

### 4.1 已具备的能力（无需改造）

- [x] Ollama 本地 Embedding 客户端（`OllamaEmbeddingClient`）
- [x] 多模型优先级路由与自动降级（`RoutingEmbeddingService`）
- [x] 云端/本地模型配置切换（`AIModelProperties` + YAML 配置）
- [x] 文档删除时同步清理向量（`KnowledgeChunkServiceImpl`）
- [x] RBAC 权限控制（`AccessControlService`）
- [x] 向量空间与知识库绑定（`collectionName` 机制）

### 4.2 建议新增的能力

| 优先级 | 改造项 | 说明 | 涉及文件 |
|--------|--------|------|---------|
| P0 | Embedding 调用审计日志 | 记录每次调用的模型、数据量、时间，不记录原文 | `RoutingEmbeddingService` |
| P0 | 云端 Embedding 开关 | 生产环境配置强制禁用云端模型 | `application.yaml`、`AIModelProperties` |
| P1 | 敏感数据脱敏层 | 在 Embedding 前对文本做实体脱敏 | 新增 `SensitiveDataMasker`，修改 `ChunkEmbeddingService` |
| P1 | 向量加密存储 | pgvector 列级加密 | `PgVectorStoreService`、`schema.sql` |
| P2 | 检索接口权限校验 | 确保 RAG 检索走 knowledge:read 权限 | `PgRetrieverService` 或 Controller 层 |
| P2 | 数据留存定时清理 | 过期审计日志和向量数据清理 | 新增定时任务 |

### 4.3 网络安全加固

| 措施 | 说明 |
|------|------|
| Ollama 内网部署 | 仅允许应用服务器访问 Ollama 端口，不暴露公网 |
| 专线/VPN | 如必须使用云端 Embedding，通过专线连接，不走公网 |
| 防火墙规则 | 限制 Embedding 服务端口的访问来源 |
| HTTPS 强制 | 云端 API 调用强制使用 TLS 加密传输 |
| API Key 管理 | 使用环境变量/密钥管理系统注入，不硬编码在配置文件 |

## 五、总结

对于 ai-shopping-agent 知识库平台，**本地 Embedding 是最佳隐私保护方案**。系统当前架构已天然支持 Ollama 本地优先 + 云端降级的路由策略，只需在生产环境确保：

1. Ollama 服务可用且配置为默认模型
2. 云端 Embedding 候选项保持 `enabled: false`
3. 增加 Embedding 调用审计日志
4. 网络层面隔离 Ollama 服务

这四步即可实现**数据全链路不出内网**的企业级隐私保护。
